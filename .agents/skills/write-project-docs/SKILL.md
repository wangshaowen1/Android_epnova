# 项目文档治理

只沉淀长期有效、无法从代码直接恢复的知识。以决策密度和检索效率衡量文档，不以覆盖率和篇幅衡量。

## 1. 判断是否需要文档

先读仓库规则和已有的 docs/README.md。只有命中以下至少一项时，才新建或保留项目文档：

- 定义架构、公共契约、持久化模型或跨功能不变量。
- 跨模块或跨端，或者存在复杂状态机、异步、并发、生命周期、迁移、兼容、回滚、安全、隐私、支付或性能风险。
- 存在多个合理方案，后续维护者需要理解选型依据。
- 预计跨版本迭代，或需要交接给其他开发者。
- 误解设计造成的成本明显高于维护文档的成本。

文案修改、样式微调、简单跳转、局部 Bug、沿用成熟模式的线性需求不建立文档。准入不通过时，简短说明原因即可。

## 2. 建立最小事实集

1. 通过文档索引和 `rg` 定位当前领域，不预读整个 docs。
2. 只读取足以核实设计的代码、契约和测试；代码证明当前实现，不自动代表目标设计。
3. 将当前事实、已确认目标和实现状态分开。尚未确认且会改变方案的内容移入“待确认问题”，不得写入目标设计。
4. 现有目录能承担下述职责时沿用，不为套模板重排文档。
5. 跨项目同步时先区分通用文档规则与项目事实：可复用规则可回推模板；产品需求、原型链接、资源及实现进度留在所属项目，代码锚点按目标仓库重新核实。

## 3. 选择稳定位置和唯一类型

新仓库默认使用以下语义结构：

```text
docs/
├── README.md                  # 项目地图和有效文档索引
├── architecture/
│   └── <topic-slug>.md        # 长期有效的边界和不变量
├── features/
│   ├── <feature-slug>.md      # 简单功能：需求和方案合并维护
│   └── <complex-feature>/     # 仅当需求和方案需要独立维护
│       ├── README.md          # 当前需求基线和功能入口
│       └── solution.md        # 需要独立维护的技术方案
├── contracts/                 # 可选：多个模块或系统共同依赖的契约
│   └── <contract-slug>.md
└── archive/                   # 已失效且仍有历史价值的文档
```

- 默认保持扁平；只有同一主题存在多份可独立阅读的文档或本地资源时，才增加主题目录。
- 简单功能默认使用 `features/<feature>.md`。当前需求基线和解决方案需要独立维护时，使用 `features/<feature>/README.md` 与 `solution.md`；按[复杂功能模板](references/feature.md)的判据选择，并在功能扩展后重新评估，不能只因篇幅短或先做底层能力而一直合并。两份文档不得重复正文。
- 路径使用稳定的英文小写 `lower-kebab-case`。
- 目录不使用版本号、开发者或实现阶段。
- 只使用仓库相对链接和相对代码路径，不记录任何开发机器绝对路径。
- 同一能力跨版本迭代时更新原文档，不按版本、开发者或实现阶段复制新文档。

先确定唯一类型，再只读取对应参考；不要加载其他模板：

- docs/README.md：读取[项目导览模板](references/overview.md)。
- 长期系统或业务域边界：读取[架构文档模板](references/architecture.md)。
- 需要与实现持续对齐的复杂能力，或需要判断需求与方案是否拆分：读取[复杂功能模板](references/feature.md)。
- 多个模块或系统共同依赖的接口、事件或数据语义：读取[契约文档模板](references/contract.md)。
- 审计、批量收敛或归档旧文档：读取[审计与归档流程](references/audit-and-archive.md)。

除归档说明外，有效文档使用以下元数据：

```yaml
---
title: <标题>
type: overview | architecture | feature | contract
status: draft | active | deprecated
last_verified: YYYY-MM-DD
---
```

复杂功能增加 `implementation: planned | in-progress | complete`；确有适用边界时增加 `applies_to`；废弃文档通过 `replacement` 指向替代文档。

## 4. 写作和压缩

- 记录目标、范围、职责、状态归属、关键流程、不变量、决策、失败行为和验证证据中与当前主题有关的部分。
- 只引用少量稳定的模块、包、入口、Schema 或测试，不记录行号和完整文件清单。
- 图或表必须比文字更短、更清楚；简单线性流程直接使用文字。
- 可选章节没有实质内容时省略。

以下内容应删除或改为链接：

- 按类、方法、页面或字段逐项讲解；
- 穷举当前已有能力、接口或文件；
- 已有权威来源的完整 API Schema；
- 写给 AI 的逐步编码指令；
- 在多篇文档中重复的全局规则、验收标准和背景；
- 重复 commit 内容的 Changelog；
- 与当前方案无关的远期设想。

长度只设软上限，不设最低行数：

| 类型 | 软上限 |
| --- | ---: |
| 项目导览 | 180 行 |
| 复杂功能 | 250 行 |
| 架构文档 | 350 行 |
| 契约文档 | 400 行 |
| 归档说明 | 40 行 |

超过预算时，先删除可从其他事实源恢复的细节，再考虑拆分。只有子主题拥有独立生命周期或会被频繁单独引用时才拆分文档。

## 5. 维护状态和一致性

- `draft`：讨论稿，不作为编码依据。
- `active`：已确认，是所描述目标和决策的有效依据。
- `deprecated`：仅保留历史背景，必须指向替代文档。

- 用代码判断当前实现，用 `active` 文档判断已确认目标。
- `implementation: complete` 与代码冲突时，必须报告差异，不得静默选择一方。
- 影响行为的代码与文档在同一次变更中更新。
- 只有核对相关代码、契约或测试后才能更新 `last_verified`。
- 编辑历史交给 Git；正文只保留无法从 diff 还原的关键决策原因。
- 新建、重命名或废弃文档时，同步更新 docs/README.md 索引。

## 6. 验证

运行确定性审计：

```text
python <skill-dir>/scripts/audit_docs.py <repository-or-docs-path>
```

长度和命名只触发复核；缺少必需元数据、相对链接失效和包含机器绝对路径属于错误。

完成前确认：

- docs/README.md 能把开发者和 AI 路由到完成任务所需的最少文档。
- 文档能回答当前主题的边界、事实源、关键状态或流程、失败行为和验证方式。
- 当前事实、目标设计和实现状态与证据一致。
- 文档组织符合当前维护需要；已拆分功能的架构图、技术取舍和源码参考归入 solution，README 保留需求及方案入口。
- 正文没有大段代码复述、重复 Schema、实现步骤清单或版本流水账。
