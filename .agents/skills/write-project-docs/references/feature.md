# 复杂功能模板

用于一个边界明确、需要与实现持续对齐的复杂能力。跨版本迭代时更新原文档。

## 先决定写一份还是两份

- 需求和方案适合一起阅读、修改和验收的简单功能，默认使用 `features/<feature>.md`。
- 需求基线与技术方案会被不同角色独立引用、更新节奏不同，或方案需要独立修改和验证时，使用 `features/<feature>/README.md` 与 `solution.md`。例如产品规则需要稳定作为验收依据，而实现还要独立维护分层、实例状态、持久化兼容和系统恢复机制；即使当前只实现无 UI 的基础能力，也应按维护需要拆分。
- 需求或实现扩展出新的状态、恢复、迁移或跨模块接入规则时，重新判断是否仍适合单文件；篇幅、类数量、有无页面及是否独立工程模块都不能单独决定复杂度。
- 拆分后，`README.md` 是功能入口和当前需求基线；`solution.md` 记录复杂解决方案。`docs/README.md` 默认只链接功能目录的 `README.md`，由该入口说明何时继续读取方案。
- AI 从原型提取的页面、状态、文案、交互和跳转先整理成当前需求，不机械复制完整原型。原型仍是产品事实来源，文档记录经过确认且会影响开发的内容。
- 开发中的 `README.md` 和 `solution.md` 属于当前文档，不能因为标题带有版本号就放入归档。

拆分时按下面分工，避免两份文档重复：

| 文档 | 记录什么 | 不记录什么 |
| --- | --- | --- |
| `README.md` | 目标、范围、原型确认后的页面职责与业务规则、主要状态、验收条件、待确认项 | 模块分层、详细技术流程和历史版本流水账 |
| `solution.md` | 模块职责、简易架构图、状态归属、关键流程、异常恢复、技术选型与源码参考、验证方式 | 重复需求正文、完整原型文案和逐文件实现步骤 |

已形成且对实现判断有用的架构图应落入方案正文，不能只留在会话回复中。合并文档将其放在实现方案部分；拆分文档将其放在 `solution.md`，需求入口只保留链接，不复制图和技术说明。

解决方案如果已经变成多个功能共同遵守的长期边界，应移到 `architecture/`；如果变成多模块或多端共同遵守的接口、事件或数据规则，应移到 `contracts/`，功能文档只保留链接。

```markdown
# <功能名称>

## 目标

说明用户或系统最终获得的结果。

## 范围与非目标

- 包含：
- 不包含：

## 当前事实与约束

只记录会实质影响目标设计的现有行为和依赖。

## 目标设计

说明职责划分、状态归属和最小必要组件关系。

## 关键决策

只记录存在可行替代方案、且取舍会影响后续维护的决定与原因；没有则省略。

## 关键流程与状态

只保留容易误解的时序、状态机、异步或并发过程。

## 失败与恢复

只记录会改变方案的失败、降级、重试、幂等、回滚或状态恢复边界；常规错误提示无需罗列。

## 契约与依赖

链接 API、Schema、设计稿或产品资料，只补充这些来源无法表达的业务语义。

## 验收与验证

列出可观察验收条件和对应验证证据。

## 实现对齐

| 关注点 | 稳定代码锚点 | 状态或偏差 |
| --- | --- | --- |

只记录 `planned`、`in-progress`、`complete` 或有意偏离目标的部分。

## 风险与待确认问题

只保留会改变实现或验收的问题，并说明未确认会影响什么、由什么条件或决定解除；没有则省略。
```
